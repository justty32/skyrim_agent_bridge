# tidy／content-trim — 內容精簡（檔內只留現行結論）

[tidy](README.md)｜原則 5 的細則

整理一份檔時，刪掉檔內的過往記錄，只留現行結論並寫精簡；**使用者原文逐字保留**；刪掉的靠 git 歷史找。整份過時的檔照原則 1 封存，本檔管的是**檔內**的段落。現行結論的意思不能變（不改原意），只刪歷史、不改結論。

## 留什麼、刪什麼

判準：**拿掉這段，照這份檔做事的人會不會做錯？** 會 → 結論，留，改寫成現在式；不會、只是說明怎麼走到這裡 → 歷史，刪。

留（結論）：

- 現在有效的規則、做法、決定、數值、路徑、欄位名、預設值；使用者說「照建議」採納的 AI 建議也算決定。
- 規則的適用條件與例外，寫成條件句，不寫成故事。
- 會再踩的坑，寫成「做 X 時要 Y」。
- 使用者原文（見下節）。

刪（歷史）：

- 決策過程：利弊表、比較過的方案、AI 寫的「為什麼這樣定」。
- 已作廢的方案、被推翻的舊版、刪除線段落（直接刪，不標刪除線留著）。
- 演變史：「某日改成…後來又…」「原本…現在…」「第 N 版」。
- 踩坑經過：誰、哪天、哪一批、當時的數字。
- 審查意見、探針結果、「這裡是某某 commit 改的」這類註記。

## 使用者原文怎麼認、怎麼留

認法（任一條成立就算）：

- 標「使用者原文」「原文」的段，或 `>` 引用區塊裡標明是使用者說的。
- 引號（「」、""）裡的話，前後標明是使用者說的：「使用者 <日期>「…」」「他說：「…」」。
- 標了使用者日期說的話（「（使用者 <日期> 定）」後接的原話）。
- 使用者親手寫的檔或段落。
- 拿不準是不是原文 → 當原文留。

留法：逐字，錯字、標點都不改；原話附帶的日期和一句「在什麼場合說的」可以留（讀懂原話需要）。原文後面 AI 寫的「所以…」改寫成現行結論。**被使用者後來的話推翻的舊原文可以刪**，只留現行那句原文＋結論；舊原文只有一部分被推翻，留還有效的那部分。

## 哪些檔適用

適用：規矩與流程檔（`workflows/` 各工作流、STRUCTURE、WORKFLOWS、INDEX、`common/user.md` 偏好、各 gotchas）、專案自己的概念／規範／設計文件與 README、討論稿；會議或評審類的場次紀錄也適用（只留裁決、收穫的坑／好處／壞處、成形的方向、待決問題與使用者原文，刪各輪過程與被後續推翻的提案）。

不適用（本來就是紀錄，價值在時間順序）：

- 日誌與報告：`session_logs/` 的每日檔（月結時收成月摘要，見 [STRUCTURE 日誌寫法](../../STRUCTURE.md#日誌寫法)，判準與原文檢查用本檔）、交接檔、整理／派線的 `reports/`、`done/`、`superseded/`、`inbox/` 的信。
- `archive/`：凍結，不改。
- `SESSION-LOG.md`、`WAIT_USER.md`：本來就只列 open、完成即刪，不另精簡。

## 怎麼做

1. 這是改條文：派能改條文的模型，不派只做雜活的便宜模型；提示附本檔。
2. 跟搬檔、拆檔分開 commit；commit 訊息寫「內容精簡」與檔名，之後 `git log --grep 內容精簡 -- <檔>` 找得到。檔內不寫「舊版見某 commit」。
3. 要找刪掉的內容：`git log -p -- <檔>`，或 `git log -S '<關鍵字>' -- <檔>`。
4. 刪標題前先 `grep -rn '<檔名>#'`：被別處錨定的標題原文保留（含標題裡的日期），或留同名 `<a id>`，或同步改指。
5. 驗原文沒丟（引號裡的；引號外的原文人工對；印出的每一筆要嘛不是使用者原文，要嘛是被推翻而刪、列在報告裡）：
   ```bash
   git show HEAD:<檔> | grep -oP '「[^」]+」' | sort -u | while IFS= read -r q; do grep -qF -- "$q" <檔> || echo "LOST $q"; done   # → 0 行
   ```
6. 掃殘留歷史：`grep -nE '~~|後來|原本|舊版|被推翻|改成|第.版' <檔>`，每一筆要嘛在原文裡，要嘛已是現在式的結論。
