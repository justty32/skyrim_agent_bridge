# STRUCTURE — 結構整理參考（被動 / 按需取用）

[INDEX](INDEX.md)｜派發 [WORKFLOWS](WORKFLOWS.md)

**被動參考**：只在你要**重構 / 整理結構**（拆大檔、分類雜亂資料夾、長出新工作流、封存過時文檔）時取用。本檔是專案組織原則的**唯一出處**，其他檔只連過來、不重述；always-on 鐵律在 AGENTS.md。

---

## 分層原則

1. **分層樹**：整個專案文檔是一棵樹，每層**只指向下一層、不存下層細節**：
   ```
   AGENTS.md（最頂，薄路由器）→ WORKFLOWS.md（依意圖派發）/ INDEX.md（結構地圖）
     → 各工作流入口（README 或單檔）→ 工作流內容 → 子工作流…
   ```
   往下走才找細節；下層檔**不向上連 AGENTS.md**。
2. **檔名語意**：**README**＝初入一個資料夾先讀的入口／導引；**INDEX**＝描述該資料夾頂層結構的索引。小資料夾兩者合一，大了才分出獨立 INDEX。
3. **durable 知識歸層**：每份長期知識歸到它所屬的那個工作流／那一層，**絕不往上堆**——AGENTS.md 因此永遠很薄。
4. **活狀態只列 open**：進度記 `SESSION-LOG.md`、等使用者的記 `WAIT_USER.md`，**完成即刪**；「改了什麼」交給 git log，決定記 `workflows/decisions.md`；檔內只留現行結論（[tidy 原則 5](workflows/tidy/content-trim.md)）。兩者膨脹就分別拆 `session_logs/`／`wait-user/`，hub 只留導航表；日誌寫法見下方[日誌寫法](#日誌寫法)。
5. **鐵律極少而 always-on**：3–5 條任何時刻都適用的規矩常駐 AGENTS.md，其餘一切按需取用。

## 結構整理原則（膨脹即拆 / 雜亂即分類）

兩個觸發、同一套方法：

- **觸發 A：單體過大**，門檻依內容性質分：
  1. `workflows/` 流程文檔單檔 > **8192 bytes**（`wf-lint` 會掃）；
  2. 使用手冊 / 產品文檔單檔 > **300 行**；
  3. 程式碼單檔 > **300 行**；
  4. **條列式區塊 > 1024 bytes**（表格／清單，每列同一組欄位）→ 抽成資料檔，不管整檔多大。**連結表**不看 bytes，超過**十條**才考慮，並看給誰用：給人導航的（路由表、目錄表、派發表）留 md、走一般 8 KB 上限（超了就分層，上層只列子層入口）；給 AI 消化的（候選表、ledger 裡的連結欄）才抽資料檔；
  5. 一個資料夾裡 **< 1 KB 小檔太多** → 合併（內容保留、原檔消失）。

  門檻是**觸發檢視的訊號**、非硬性上限：本質不可分的單體（一份完整 spec／plan、一篇連貫的調查筆記）可超標保留；**已完成的 spec/plan 一律移 `archive/` 凍結**。
- **觸發 B：資料夾雜亂**：一個資料夾裡散落**不同用途**的檔案才拆；**同類檔案**（同一系列 log／報告）可以放鬆，不必為了檔數硬拆。

方法（兩種觸發都照做）：

1. **按內容／職責／用途語意分**，不是硬切等分——每塊要有單一清楚的職責。
2. 放進**專屬子資料夾**（或既有領域檔）依用途歸類。
3. 子資料夾頂層留 **README / INDEX** 做導航，已有就更新。
4. 原位置只留**精簡指標＋指向 index 的連結**，不再塞細節。
5. **整檔 >8 KB 拆資料夾時原路徑保留當入口**（外部連結不斷）。

## 一個工作流的成長軌跡（四級）

工作流**按需要逐步長出來**，每升一級都是「膨脹即拆」的套用：

1. **單檔**：一個 `.md`，**檔名即其意義**（如 `testing.md`），導引、結構、內容揉在一起。多數工作流停在這。
2. **資料夾＋單 README**：膨脹到要拆 → 變資料夾，裡面**只有 `README.md`**，仍一肩扛導引＋細則＋結構。
3. **資料夾內不只 README**：README 再膨脹 → 拆出獨立檔各司其職：`INDEX.md`（結構）、`session-log.md`（本工作流 open 進度）、`gotchas.md`、內容檔…，README 退回只做「先讀我」。
4. **資料夾內有子工作流**：內部再開巢狀工作流，各子工作流自己又從第 1 級開始長。

走到哪一級由「是否膨脹 / 雜亂」決定，不預先過度設計。**降級也成立**：子項消失就往回併級。

## 工作流的統一形式

- **入口檔段落**固定，照 [workflows/TEMPLATE.workflow.md](workflows/TEMPLATE.workflow.md)：何時用 ↔ 何時不用 / `Done when:` / 流程 / 交接。既有工作流的入口檔下次動到時再補齊，不為了補而改。
- **`Done when:` 只准三類可觀察條件**：檔案存在、指令回傳、表格填滿（✗「功能做好」這種不可觀察的）。
- **資料夾型**：入口 `README.md` ＋視需要的 `archive/`、`gotchas.md`、`session-log.md`；**單檔型**：一個 `.md` 同時是入口與內容，撐大了照上面四級成長升級成資料夾型。有哪些工作流看派發表。

## archive 規則

- 過時 / 被取代的文檔搬進**所屬工作流**的 `archive/`（共享的進 `common/archive/`），**不刪**、不在維護鏈。
- 檔名保留原名；檔頭第一行加 `> 封存 YYYY-MM-DD，由 <取代它的路徑> 取代`（沒有取代者就寫原因）。
- **指向被封存檔的連結從活文件拿掉**（改純文字或刪句），**當它不存在**；不改指到 `archive/` 路徑。
- `archive/` 內**只有 `README.md` 索引**（可省略；一列一檔：檔名、封存日期、取代者或原因；**只准追加列**），是唯一可以連進 `archive/` 的地方；不套大小門檻、不維護內部連結。
- 工作流若依協議用 `done/`／`superseded/` 分層（如 dispatch 的 handoff），同樣視為封存、不套門檻、lint 不下鑽；放信的 `inbox/`（含 `done/`）是寄件原文、比照處理（`workflows/inbox/` 是工作流文件，照掃）。

## 日誌寫法

專案若記日誌（`session_logs/`），它只記「哪天做了什麼」，**不是第二份知識庫**：

- **每日檔少寫**：`session_logs/<月>/<日期>.md` 每條一行「動了哪些檔／做了什麼」＋連到結論所在處。結論寫進它自己的文件，日誌只連過去；沒有別的家可放的（代定清單、當天交接）才寫在日誌裡。
- **總目錄**（`session_logs/README.md`）每天一列，寫一句「這天定下了什麼」（結論），不列做了哪些事；連到該日檔，已收月摘要的連月摘要的該日段。
- **月摘要**：月結後把該月每日檔濃縮成 `session_logs/<月>.md`：每天一段 `## <日期>`，只留結論（別處已有就連過去）與使用者原文，判準與原文檢查照 [tidy 內容精簡](workflows/tidy/content-trim.md)，commit 訊息寫「內容精簡」。被連過的舊錨點在月摘要保留同名標題或 `<a id>`。每日原檔照 archive 規則封存到 `session_logs/archive/<月>/`，活文件裡指向它的連結改指月摘要同名段。
